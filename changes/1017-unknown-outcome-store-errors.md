section: Changed
issue: 1017

**A store error whose outcome is unknown hands the tree over, as a timeout does** (#1017): a store call can fail after its write reached the database — a COMMIT applied, then the connection reset — and until now that surfaced as an ordinary store error: the step failed, and `.onError` and the undo of earlier steps ran for an order whose charge had committed. A store that finds such an error now throws `StoreOutcomeUnknownError` (`source: StoreOutcomeSource.Transport`), and under a lease the framework hands the tree over exactly as for a timeout: the lease is abandoned, nothing is undone, no failed record is written, and the next holder reconciles (the fenced effect's row is replayed, a pending outbound intent is reconciled, the latest checkpoint is resumed). Unleased, the error passes through as it is; an error whose outcome is known (nothing was sent, or the database refused the statement) still fails as before. The SQLite stores classify their own: a COMMIT that fails with anything but `SQLITE_BUSY` or `SQLITE_CONSTRAINT` (the transaction stays open, nothing was applied), and a single write outside a transaction that fails with an I/O error, are of unknown outcome; the in-memory stores have nothing to classify. A new log code, `store.outcome-unknown`, says which call was read that way, and a store method that throws it synchronously (not `async`) is handed over like one that rejects. For store authors: `fencedEffectContract` gains a case (the effect's work throws `StoreOutcomeUnknownError`: it must reach the caller as it is, the effect rolled back), and the fault suite gains scenario 23 and its sabotage; a store set over TCP gets the lost answer from `DatabaseProxy.dropAfter`. The PostgreSQL, MongoDB and Redis packages classify their transport errors in their own releases.
